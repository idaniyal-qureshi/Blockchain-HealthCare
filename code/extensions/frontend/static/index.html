How a record is released

Four checks between a request and the data

  1. 1
    Authorisation proofThe hospital shows the patient’s token: H(s′) must equal p, retried up to k times (Algs 3–4).
  2. 2
    Patient policyEntity, role, resource, access and expiry must match the patient’s latest policy (Eqs 8–10).
  3. 3
    Consensus commitThe decision is written to the ledger through Raft; a compromised leader’s block is rejected (Eq 11).
  4. 4
    Decrypt & releaseOnly then are the record’s Kyber-inspired ciphertexts opened for the hospital.
Baseline mode

Reproduced as published, flaws included

This is the reference paper’s design: Kyber-inspired mock encryption, hash-commitment authorisation and Raft consensus. It is deliberately as insecure as that design. A captured token replayed with a fresh nonce, and a policy token copied from the public ledger, are both accepted; the admin portal’s attack lab shows it.

All names in the demo accounts are fictional.
